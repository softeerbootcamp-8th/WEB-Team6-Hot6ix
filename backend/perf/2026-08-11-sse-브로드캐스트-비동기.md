# SSE 브로드캐스트 비동기 전환 부하 측정 (after)

- 측정일 2026-08-11 21:45 ~ 22:01
- before 는 [2026-08-11-sse-브로드캐스트-동기.md](2026-08-11-sse-브로드캐스트-동기.md)
- 코드 변경 `RoomSseManager.sendBroadCast()` 의 전송 루프를 `SseBroadcastExecutor` 로 넘겼다.
  순번 발급(`sseEventBuffer.add`)은 요청 스레드에 남겼다 — `Last-Event-ID` 가 커밋 순서대로
  매겨져야 하기 때문이다. 실행기는 풀 2, 큐 1000, `CallerRunsPolicy`(`SseBroadcastConfig`)
- 계측 추가 `upbid.sse.broadcast.queue`(큐 대기), `upbid.sse.broadcast.caller.runs`(호출
  스레드가 직접 쏜 횟수). 이유는 아래 "왜 큐 대기를 따로 재는가"

## 결론 먼저

**전송이 입찰 응답 경로에서 빠졌다.** 브로드캐스트 비용이 늘어날 때 입찰 응답이 흡수하는
비율이 **136% → 32%** 로 떨어졌다.

**처리량이 개선됐다고는 말할 수 없다.** 비동기 계열의 접수율이 before 의 7분의 1이라
브로드캐스트 부하 자체가 7배 가벼웠다. 일을 옮긴 것이지 줄인 것이 아니므로, CPU 총량은
그대로다. 자세한 것은 "이 측정이 답하지 못한 것".

## before / after 비교

### 핵심 — 브로드캐스트 증가분이 응답에 얹히는 비율

100 → 400 구간을 쓴다. 이 구간은 **양쪽 다 접수율이 통제된다**(동기 134.5 → 121.7건/s = −10%,
비동기 19.0 → 18.9건/s = −0.5%).

| | broadcast p50 증가 | 접수 p50 증가 | 얹힌 비율 |
|---|---|---|---|
| **동기 (before)** | +6.99 ms (1.94 → 8.93) | **+9.53 ms** (14.09 → 23.62) | **136%** |
| **비동기 (after)** | +6.23 ms (2.08 → 8.31) | **+2.01 ms** (11.80 → 13.81) | **32%** |

### 남은 +2.01 ms 는 무엇인가

접속 100 → 400 에서 접수 p50 이 2.01 ms 올랐다. 후보는 셋이고 **분리하지 못했다.**

- 브로드캐스트 CPU 경쟁 — 전송 스레드가 0.06 → 0.21 초/초를 쓴다(2코어 중 3 → 10%)
- 힙 130 → 175 MB 에 따른 GC 압력

거절 p50 이 거의 안 움직인 것(7.98 → 8.13)을 보면 서버 전체가 느려진 것은 아니고, **접수된
요청에만 붙는 무언가**다. 다음 측정에서 볼 것으로 남긴다.

## 왜 큐 대기를 따로 재는가

`upbid.sse.broadcast` 는 전송 루프만 잰다. 동기였을 때는 큐가 없어서 그 값이 곧 이벤트 도달
시간이었지만, 비동기에서는 **큐 대기 + 전송**이 도달 시간이다. 안 재면 "입찰은 빨라졌는데
이벤트가 늦게 도착하는지"를 알 수 없다.

`CallerRuns` 카운터가 짝으로 필요한 이유: 큐가 넘쳐 호출 스레드가 직접 실행하면 대기가
0으로 찍힌다. 그러면 대기 0이 "큐가 한가하다"인지 "비동기가 아니었다"인지 구분되지 않는다.

### 실측 결과 — 대기는 사실상 없다

평균 0.06 ~ 0.14 ms. `CallerRuns` 0.

**단, 이 값은 큐를 시험한 결과가 아니다.** 아래 참고.

주의: 큐 대기의 p50·p95 가 세 실행 모두 정확히 0.50 / 0.95 ms 로 찍혔다. 이는 Micrometer
히스토그램의 **최저 버킷 경계값**이고, 실제 분포가 그보다 아래라 분위를 못 재는 것이다.
이 지표는 **평균으로 읽는다.**

## 이 측정이 답하지 못한 것

### 처리량 개선은 주장할 수 없다

| | 접수/s | 브로드캐스트 스레드시간 (sse400) |
|---|---|---|
| 동기 | 121.7 | **1.41 초/초** (2코어의 70%) |
| 비동기 | 18.9 | **0.21 초/초** (2코어의 10%) |

비동기 계열이 브로드캐스트를 **7배 덜 했다.** 처리량이 1,451 → 2,683 req/s 로 보이는 것은
대부분 이 차이다. 비동기화는 CPU 일을 줄이지 않으므로, 같은 접수율에서 재면 처리량은
비슷할 것으로 본다.

### 2스레드로 충분한지 모른다

큐가 한가한 이유는 들어오는 일이 0.21 초/초뿐이어서다. 동기 계열 수준(1.41 초/초)이면
2스레드(최대 2 초/초) 사용률이 70%가 되고, 그 지점에서는 대기가 전송 시간과 맞먹을 수 있다.
**접수율이 높은 상태로 다시 재야 답이 나온다.**

### 접수율이 왜 7배 떨어졌는가

동기 3줄이 121~153건/s, 비동기 4줄이 18.6~21.3건/s 로 일관되게 갈렸다. 우연으로 보기 어렵다.

`bid.js` 의 금액이 `START_PRICE + BID_UNIT * (__ITER * VUS + __VU)` 로 그 VU 의 반복 횟수에
묶여 있다. 접수 응답이 빨라지면 앞서간 VU 가 더 빨리 반복하며 금액 격자를 독점하고,
나머지 VU 는 계속 `BID_AMOUNT_TOO_LOW` 로 거절된다. **비동기화가 접수율을 떨어뜨린 것으로
보인다.**

서비스 관점에서는 문제가 아니다 — 실제 사용자는 `__ITER` 격자로 입찰하지 않는다. 이건
부하 스크립트의 인공물이다. **측정 관점에서는 동기·비동기 절대값을 비교할 수 없다는 뜻**이고,
그래서 판정을 계단 안의 기울기로 잡았다.

## 다음에 할 것

### 1. 접수율을 높인 상태로 다시 잰다 (가장 급함)

위의 미해결 셋(처리량, 2스레드 충분한지, CPU 경쟁)이 전부 이것 하나에 달려 있다.

**VU 마다 자기 물품에 입찰**하게 하면 금액 격자 충돌이 없어져 접수율이 100%에 가까워진다.
물품 40개 + VU 40, `perf` 프로파일이 `max-in-progress-per-room: 50` 이라 가능하다.
`bid.js` 는 물품을 랜덤으로 고르므로(시나리오 1·2 대조가 걸려 있어 고치지 않는다)
새 스크립트가 필요하다.

### 2. 방별 순서 보장 — 실서비스 적용 전 필수

스레드가 2개라 같은 방의 두 이벤트가 순서를 바꿔 도착할 수 있다. 클라이언트가
`Last-Event-ID` 로 복구하므로 순서가 어긋나면 복구 지점이 틀어진다. `roomId` 해시로
파티션된 실행기가 필요하다(`SseBroadcastConfig` javadoc 의 미해결 항목).

**이 측정에서는 배경 SSE 가 순서를 검증하지 않아 숫자는 유효하다.**

### 3. 일 자체를 줄인다 — 재직렬화 제거

`emitter.send(SseEmitter.event().data(dto))` 는 `ResponseBodyEmitter` 가 emitter 별로 메시지
컨버터를 타므로 **같은 payload 를 접속 수만큼 다시 직렬화한다.** 400 접속이면 400번이다.
전송 1건당 20.8 µs 의 상당 부분일 가능성이 있다.

루프 밖에서 한 번 직렬화해 문자열로 넘기면 사라진다. 비동기화가 "옮기기"였다면 이건
"줄이기"고, CPU 총량을 실제로 낮추는 유일한 항목이다.

### 4. heartbeat — 별도 과제

`sendHeartbeat()` 는 여전히 스케줄러 스레드에서 전 접속에 동기로 쏜다. 접속 400에서
p95 12 ms 이고, 물품 마감 예약과 `spring.task.scheduling.pool` 을 공유한다. 접속이 더
늘면 마감이 밀린다.

## 미검증·한계

- **app CPU 가 여덟 실행 모두 100%** 다. 접속 0에서도 100%이므로 이 포화는 시나리오 1
  (vus 40, 물품 1개, 초당 2,700건 거절)의 기본 상태다. CPU 여유가 없는 지점이라
  비동기화 효과가 과소평가될 수 있다.
- **그 전송 시간이 CPU 인지 대기인지 여전히 안 갈렸다.** `ThreadMXBean` 으로 브로드캐스트
  구간의 CPU 시간을 wall time 과 나란히 재면 갈린다. 처방이 같아서 급하지 않다.
- **톰캣 스레드 풀 고갈은 재지 못했다.** `tomcat_busy_max` 41(기본 200 스레드에 VU 40).
- **느린 클라이언트가 없다.** 배경 SSE 가 루프백에서 본문을 즉시 읽고 버리므로,
  실제 모바일 사용자에서 발생할 `emitter.send()` 블로킹은 이 측정에 존재하지 않는다.
- **접수 p95·p99 는 세밀하게 읽지 않는다.** 접수 표본이 3,200~3,800건뿐이라 버킷에 걸린다
  (sse0 과 sse100 의 접수 p95 가 둘 다 정확히 56.20 ms 로 찍혔다). **p50 을 본다.**
- 큐 대기 p50·p95 는 히스토그램 최저 버킷 아래라 경계값(0.50 / 0.95 ms)이 찍힌다. 평균으로 읽는다.

## 재현 방법

`index.csv` 에 없는 열(상태 코드별 응답 분위, broadcast·큐 분위)은 Prometheus 에서 뽑는다.
컨테이너를 내리면 사라지므로 **이 문서의 표가 원본이다.**

```bash
RUN=2026-08-11T21-58-00_s1_vus40_pool10_items1_sse400
U='/api/v1/auction-items/{auctionItemId}/bids'
S=$(TZ=UTC date -j -f "%Y-%m-%dT%H:%M:%SZ" "$(jq -r .window.start perf/results/$RUN/meta.json)" +%s)
E=$(TZ=UTC date -j -f "%Y-%m-%dT%H:%M:%SZ" "$(jq -r .window.end   perf/results/$RUN/meta.json)" +%s)

# 접수(201)만의 p50. status="409" 로 바꾸면 거절
B="http_server_requests_seconds_bucket{run=\"$RUN\", uri=\"$U\", status=\"201\"}"
curl -s -G http://localhost:19090/api/v1/query --data-urlencode "time=$E" \
  --data-urlencode "query=histogram_quantile(0.5, sum by (le) (($B @ $E) - (($B @ $S) or ($B @ $E) * 0)))*1000" \
  | jq -r '.data.result[0].value[1]'
```

- 브로드캐스트 분위 → `upbid_sse_broadcast_seconds_bucket{run="$RUN"}`
- 큐 대기 평균 → `upbid_sse_broadcast_queue_seconds_sum` ÷ `_count`
- CallerRuns → `upbid_sse_broadcast_caller_runs_total`

`or ... * 0` 은 시작 시점에 없던 계열을 0으로 채운다(`run.sh` 의 `delta()` 와 같은 방식).
