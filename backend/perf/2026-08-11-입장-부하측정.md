## 1. 왜 입장을 재기로 했나

### 서비스 구조상 여기가 제일 뾰족하다

Hot6ix는 링크·QR로 참여하는 SNS 연계 경매다. 판매자가 링크를 뿌리면 몇 분 안에 사람이
우르르 들어온다. 방 자체는 작다 — 물품 20개, 참여자 200명. **데이터는 작은데 도착 속도만
튀는** 모양이고, 그게 이 서비스의 실제 리스크다.

### 그런데 기존 시나리오가 입장을 한 번도 안 때린다

`perf/k6/` 의 스크립트가 실제로 부르는 엔드포인트를 전부 뽑으면 이렇다.

```
capacity.js   -> /actuator/health
bid.js        -> POST /auction-items/{id}/bids
scenario3.js  -> GET  /auction-rooms/share/{code}/subscribe   (SSE)
scenario4,5   -> POST /auction-items/{id}/start
common.js     -> POST /auth/dev-login, .../agreement
```

**입장 경로를 부르는 스크립트가 하나도 없다.** 시나리오 0~5 는 전부 "이미 들어와 있는 사람"을
가정한다. 그래서 시나리오 6 을 새로 만들었다.

### 입장 한 번에 서버가 하는 일

프론트(`rooms.$shareCode.index.tsx`)가 마운트할 때 무조건 넷을 쏜다.

| 요청 | 무엇 |
|---|---|
| `GET /auction-rooms/share/{code}` | 방 정보 |
| `GET /auction-rooms/share/{code}/auction-items` | **물품 목록 + 리더보드** |
| `GET /auction-rooms/share/{code}/events` | 최근 이벤트 복구 |
| `GET /auction-rooms/share/{code}/subscribe` | SSE 연결 |

**리더보드는 별도 API 가 아니다.** 물품 목록 응답에 상위 3명이 딸려 나온다
(`AuctionItemService.getSummaries`). 이 사실이 이번 측정 전체의 출발점이다.

## 2. 측정 설계

### 한 반복 = 한 사람의 입장

REST 3개를 `http.batch` 로 병렬 발사한다. 브라우저가 실제로 그렇게 하기 때문이고, 순차로
보내면 VU 하나가 입장 하나에 3배 시간을 써서 같은 VU 수로도 서버가 보는 동시성이 1/3 이 된다.

SSE 구독(`/subscribe`)은 스크립트에 넣지 않았다. 끝나지 않는 스트림이라 반복마다 열면 접속이
무한히 쌓이고 응답 p95 도 그쪽으로 끌려간다. 배경 접속이 필요하면 `--sse` 로 붙인다.

세 요청에 `room` / `items` / `events` 태그를 따로 달았다. `items` 만 p95 가 튀는지 봐야
리더보드가 범인이라고 말할 수 있다.

### 함정 하나 — `seed.sh` 는 입찰을 안 만든다

`seed.sh` 가 만드는 것은 판매자 1 · 방 1 · 물품 N · 구매자 M명(+약관 동의)까지다. **입찰은
한 건도 없다.**

리더보드 쿼리는 `bids` 를 `GROUP BY` 로 훑는데, 그 표가 비면 아무것도 못 찾고 즉시 끝난다.
그대로 재면 "입장 초당 수천 건" 이 나오고 **그 줄은 겉보기에 멀쩡해서 아무도 못 알아본다.**

그래서 `--bids-per-item N` 을 만들어 입찰을 미리 채운다. 총건수가 아니라 **물품당**인 이유는,
이 값을 현실값에 고정해 두고 `--vus` 만 올리는 게 계단이라 `--items` 를 바꿔도 안 흔들려야
하기 때문이다.

### 계단을 데이터가 아니라 사람 수로 잡은 이유

처음에는 입찰 수를 계단으로 잡으려 했다(물품당 2,500건 등). 그런데 이 서비스는 물품당 입찰
수에 **구조적 상한**이 있다. `uk_bids_item_amount` 가 (물품, 금액) unique 이고 금액은
`bid_increment` 격자 위에서만 오른다. 물품당 2,500건이면 현재가가 시작가보다 단위×2,500 위
— 시작가 1만 원 / 단위 1천 원이면 **250만 원짜리 물건**이다. 데이터를 부풀린 게 아니라 다른
서비스를 재는 것이 된다.

그래서 **물품당 200건(현실값)에 고정하고 VU 만 올리는** 설계로 바꿨다.

## 3. 측정을 시작하기 전에 도구에서 찾은 것 둘

시나리오 0(부하 발생기 한계)을 한 줄 돌렸더니 계측 도구 자체의 문제가 먼저 나왔다.

### 3-1. 워밍업이 아무것도 하지 않았다

`run.sh` 의 워밍업 단계 전체가 `sleep "$WARMUP"` 이었다. **부하를 걸지 않는다.** 그래서 k6 가
시작할 때 JVM 이 완전히 차갑고, 측정 구간 앞부분이 그대로 워밍업 구간이 된다.

`2026-08-11T10-58-15_s0_vus160_pool10_items1_sse0` 의 시계열:

```
0 -> 797 -> 2513 -> 4520 -> 8859 -> 13839 -> ~15000 (평평)
└──────────── 약 40초 ────────────┘
```

| | req/s |
|---|---|
| `index.csv` 에 찍힌 값 (182초 전체 평균) | 11,774.9 |
| 정상 구간 평균 | 13,356 |

**보고값이 정상 상태보다 12% 낮았다.** 37개 표본 중 8개(구간의 22%)가 아직 덥혀지는 중이었다.

계단 비교("두 배 올렸는데 몇 배")가 이 값으로 이뤄지는데, 계단마다 콜드 구간이 차지하는 비중이
다르면 그 비율이 왜곡된다. **`results/` 안의 이전 측정은 전부 이 영향을 받았다.**

→ `perf/k6/warmup.js` 를 만들어 워밍업 동안 실제로 부하를 걸게 고쳤다. 읽기 전용 둘만 때린다
— 시나리오 자기 스크립트로 덥히면 입찰이 `current_price` 를 올려서 본 측정의 첫 입찰들이
전부 거절되고, 마감 스크립트는 물품을 미리 닫아 버린다.

**수정 후 시나리오 6 시계열:** `255 -> 282 -> 340 -> 325 -> ~315` (램프 8% 이내로 사라짐)

### 3-2. `/actuator/health` 가 DB 를 탄다

`capacity.js` 주석은 "여기는 DB 도 락도 안 타므로" 라고 적혀 있었는데 **사실이 아니다.**
Spring Boot Actuator 의 기본 db health indicator 가 요청마다 DataSource 검증 쿼리를 날린다
(`application-perf.yaml` 에 이를 끄는 설정이 없다).

시나리오 0 구간에는 health 말고 다른 트래픽이 없는데도:

| | |
|---|---|
| `hikari_active` | 평균 5.3, **최대 10 (풀 상한)** |
| `hikari_pending` | 최대 68 |

즉 시나리오 0 이 재는 것은 "순수 부하 발생기 한계"가 아니라 "health + DB 왕복의 한계"이고,
**진짜 k6 상한은 이보다 높다.** 낮게 잡히는 쪽이라 안전한 방향으로 틀리므로 동작은 그대로
두고 주석만 정정했다.

> **시나리오 0 에서 `pending` 이 보이는 것을 서비스 문제로 읽지 않는다. health 몫이다.**

### 3-3. 그래서 시나리오 0 계단은 돌리지 않았다

시나리오 0 의 목적은 "내가 잰 숫자가 서버 한계냐 노트북 한계냐"를 가르는 것이다. 부하
발생기가 15,000+ req/s 를 내고 시나리오 6 은 초당 수백 건 수준이라 **자릿수가 두 개 차이**다.
계단을 다 올려도 결론이 안 바뀌므로 건너뛰었다.

실제로 시나리오 6 의 `k6_cpu_max` 는 11~13% 였다. 부하 발생기는 내내 한가했다.

### 4-1. 계단 (#1 → #2) — 첫 doubling 에서 포화

| | vus 10 | vus 20 | 배율 |
|---|---|---|---|
| **입장 처리량** | 106.2 건/s | 107.8 건/s | **1.02배** |
| p95 (서버) | 112 ms | 313 ms | 2.8배 |
| 커넥션 획득 p95 | 78 ms | 196 ms | 2.5배 |
| `hikari_pending_max` | 9 | 39 | 4.3배 |
| `hikari_active_max` | **10 / 10** | **10 / 10** | 포화 유지 |
| 톰캣 스레드 | 20 / 200 | 50 / 200 | 여유 |
| `k6_cpu_max` | 11% | 13% | 무관 |

**부하를 2배 올렸는데 처리량은 1.02배, 지연만 2.8배.** 판정 규칙("1.2배도 안 오르는 첫 줄")에
첫 doubling 에서 걸렸다. 톰캣은 200개 중 50개만 쓰고 부하 발생기도 한가한데 처리량이 안 오른다.

계단을 80·160 까지 올릴 필요가 없어 여기서 멈추고 원인 규명으로 넘어갔다.

**입장 1회의 비용 (`select_per_bid` = 8.0 을 코드로 뜯은 것):**

| # | 쿼리 | 사람마다 다른가 |
|---|---|---|
| ① | 방 조회 (`findRoomByShareCode`) | 아니오 |
| ② | 약관 동의 여부 | **예 (사용자별)** |
| ③ | 물품 수 카운트 | 아니오 |
| ④ | `resolveRoomId` — 물품 목록에서 | 아니오 (①과 같은 값) |
| ⑤ | 물품 목록 | 아니오 |
| ⑥ | **리더보드** | 아니오 |
| ⑦ | `resolveRoomId` — 이벤트에서 | 아니오 (①과 같은 값) |

**8개 중 7개가 "같은 방이면 같은 값"이고, 방을 shareCode 로 찾는 조회가 3번 중복된다.**
(측정값 8.0 중 7개만 코드에서 짚었다. 나머지 1개는 미확인.)

### 4-2. 커넥션 풀 (#1 → #3) — 키우면 오히려 나빠진다

| | pool 10 | pool 30 | |
|---|---|---|---|
| **입장 처리량** | 106.2 건/s | **91.2 건/s** | **−14%** |
| p95 | 112 ms | **191 ms** | **+70%** |
| 커넥션 획득 p95 | 78 ms | **1 ms** | −99% |
| `hikari_pending_max` | 9 | **0** | 대기열 소멸 |

**커넥션 대기는 완전히 사라졌는데 처리량은 떨어지고 응답은 느려졌다.**

```
pool 10:  응답 112ms = 커넥션 대기 78ms + 실제 작업 ~34ms
pool 30:  응답 191ms = 커넥션 대기  1ms + 실제 작업 ~190ms
```

커넥션 대기 78ms 는 **병목이 아니라 병목 앞의 줄**이었다. 풀을 키우니 19개 커넥션이 동시에
MySQL(`cpus 2.0`)을 때려서 쿼리 하나하나가 느려졌다. 줄이 풀 앞에서 DB 안으로 옮겨갔고,
옮겨간 자리가 더 비쌌다.

> **결론: 커넥션 풀을 키우면 안 된다. 성능이 14% 깎인다.**

### 4-3. prepared statement 캐시 (#1 → #4) — +5.5%

JDBC URL 에 `characterEncoding=UTF-8` 하나뿐이라 드라이버 기본값
(`useServerPrepStmts=false`, `cachePrepStmts=false`)으로 돌고 있었다. 실행할 때마다 SQL
텍스트를 보내고 MySQL 이 매번 파싱한다.

| | off | on |
|---|---|---|
| 입장 처리량 | 106.2 건/s | **112.0 건/s (+5.5%)** |
| p95 | 112 ms | 111 ms |
| 커넥션 획득 p95 | 78 ms | 79 ms |
| `hikari_active_max` | 10 / 10 | 10 / 10 |

**+5.5% 는 진짜지만 병목을 바꾸지 못했다.** 풀은 여전히 포화, p95 도 그대로다. SQL 파싱은
병목의 5.5% 짜리 몫이었다. 설정 한 줄에 코드 변경이 없으므로 켤 만하다.

캐시가 실제로 동작하는지는 `Com_stmt_prepare` 로 확인한다 — 18만 번 실행에 prepare 는 **134번**
이었다.

### 4-4. 리더보드 (#4 → #5, #6) — 여기가 범인

| 물품 | 물품당 입찰 | **총 `bids` 행** | 입장/s | p95 |
|---|---|---|---|---|
| 20 | 200 | **4,000행** | **112.0** | **111 ms** |
| 20 | 0 | 0행 | 1,593.1 | 5 ms |
| 1 | 200 | 200행 | **1,664.7** | **5 ms** |

**쿼리 개수는 세 경우 모두 8.0 으로 같다.** 달라진 것은 그중 한 개의 비용뿐이다.

```
입장 p95 111ms  =  리더보드 106ms  +  나머지 전부 5ms
                   └── 95% ──┘
```

**물품 수는 무해하다.** 물품 20개짜리 목록도 입찰이 없으면 1,593건/s 로 멀쩡하다.

**입찰 행 수가 전부다.** 200행에서는 1,664건/s 인데 4,000행이 되면 112건/s 로 **15배 무너진다.**

> ⚠️ 이 112건/s 는 **최악 분포**(물품당 입찰자 200명)의 값이다. 같은 4,000행이라도 현실 분포에서는
> **609건/s** 다 ([4-6](#4-6-데이터-분포가-실행-계획을-바꾼다--기준선-재설정)). 이 절의 "15배"도
> 그만큼 과장돼 있다 — 현실 분포 기준으로는 1,593 대 609 로 **2.6배**다.
> **리더보드가 병목이라는 결론 자체는 양쪽에서 같다.**
데이터 20배 증가에 성능 15배 하락 — 거의 선형 이상으로 악화된다.

그리고 **4,000행은 아주 평범한 방이다.** 물품 20개에 참여자 200명이 한 번씩만 입찰한 상태다.

**왜 비싼가** — `BidRepository.findTopBidders`:

```sql
SELECT * FROM (
  SELECT b.auction_item_id, u.nickname, MAX(b.amount),
         ROW_NUMBER() OVER (PARTITION BY b.auction_item_id
                            ORDER BY MAX(b.amount) DESC, b.bidder_user_id ASC) AS rankNo
    FROM bids b JOIN users u ON u.user_id = b.bidder_user_id AND u.deleted_at IS NULL
   WHERE b.auction_item_id IN (:ids)
   GROUP BY b.auction_item_id, b.bidder_user_id, u.nickname) ranked
 WHERE rankNo <= 3
```

**입장 한 번마다 4,000행을 그룹핑·정렬해서 60행을 뽑는다.** 초당 112명이면 초당 44만 행이다.
왜 그렇게 되는지는 다음 절에서 실행 계획으로 확인했다.

> 측정 전 예측은 "현실 규모에서 리더보드는 병목이 아닐 것"이었다. **틀렸다.** 재지 않았으면
> 커넥션 풀을 키우는(−14%) 잘못된 선택을 했을 것이다.

### 4-5. 실행 계획 (EXPLAIN ANALYZE)

물품 20개 · 입찰 4,000행 상태에서 `EXPLAIN ANALYZE` 로 확인했다.

```
-> Sort (60행)
  -> Filter: rankNo <= 3 (60행)
    -> Materialize (4,000행)
      -> Window aggregate: row_number() (4,000행)
        -> Sort: item, amount DESC, bidder (4,000행)
          -> Aggregate using temporary table (4,000행)
            -> Nested loop inner join (실제 4,000행 / 추정 412행)
              -> Table scan on u (206행)              <- users 풀스캔이 바깥 루프
              -> Index lookup on b using FK1yrwjn... (bidder_user_id)
                 Filter: auction_item_id IN (...)     <- 인덱스가 아니라 필터
```

**셋이 잘못돼 있다.**

1. **리더보드용 인덱스를 쓰지 않는다.** `idx_bids_item_bidder_amount` 를 만들어 뒀는데 실제로는
   `bidder_user_id` FK 인덱스를 타고, `auction_item_id IN (...)` 은 **읽고 나서 버리는 필터**로
   적용된다 (27.2행 읽어 19.4행 남김).
2. **조인 순서가 뒤집혀 있다.** `users`(206행)를 풀스캔해 바깥 루프로 돌면서 유저마다 bids 를
   룩업한다. 물품으로 좁히고 유저를 붙이는 것의 반대다.
3. **옵티마이저가 행 수를 10배 과소추정한다** (추정 412 / 실제 4,000). 이 조인 순서를 고른
   원인일 가능성이 크다.

결과적으로 **60행을 뽑으려고 4,000행을 세 번(그룹핑 → 정렬 → materialize) 훑는다.**

#### 대안 두 개를 재봤다 (3회 반복, 단독 실행)

| | 실행 시간 | |
|---|---|---|
| **현재 쿼리** | 9.46 / 7.35 / 6.74 ms | |
| **(B) 조인 순서만 뒤집기** | 7.7 ms | 22% 개선 |
| **(C) LATERAL 물품별 상위 N** | **0.82 / 0.74 / 0.70 ms** | **약 10배** |

**(B)** — `users` 조인을 서브쿼리 밖으로 빼 60행에만 붙인다. `idx_bids_item_bidder_amount` 를
제대로 타고(`Covering index skip scan for grouping`) users 는 PK 룩업 60번으로 줄지만
**22% 개선에 그친다.** 4,000행 그룹핑·정렬 구조가 그대로이기 때문이다.

**(C)** — 물품마다 `ORDER BY amount DESC LIMIT 10` 으로 상위만 가져온다. **물품당 10행, 총 200행**만
다루므로 구조 자체가 달라진다.

```sql
SELECT i.auction_item_id, t.bidder_user_id, t.amount
  FROM auction_items i
  JOIN LATERAL (SELECT b.bidder_user_id, b.amount
                  FROM bids b
                 WHERE b.auction_item_id = i.auction_item_id
                 ORDER BY b.amount DESC
                 LIMIT 10) t ON TRUE
 WHERE i.auction_item_id IN (:ids)
```

결과도 일치한다 — 물품 1의 상위 3건이 양쪽 다 `210000 / 209000 / 208000` 이었다.

> 측정에서 리더보드가 입장당 106ms 를 먹었는데 단독 실행은 7.9ms 다. 그 차이는 경합이다
> (10 VU 가 MySQL `cpus 2.0` 을 나눠 쓴다). 단독 0.75ms 로 줄면 경합 상황에서도 비례해 줄어든다.

#### (C) 의 정확성 주의

리더보드는 **서로 다른 입찰자 상위 3명**이다. 상위 10건을 가져와 중복 제거하면 3명이 안 나올 수
있다 — **두 사람이 치열하게 주고받으면 상위 10건이 그 둘의 것**일 수 있다.

시드 데이터는 입찰자당 물품마다 1건뿐이라 이 경우가 나오지 않았다. 실제 경매에서는 나오므로
최종 구현에서 설계가 필요하다.

- `LIMIT` 를 넉넉히 (20~30) — 그래도 4,000행보다 훨씬 싸다
- 그래도 3명이 안 되면 fallback
- "3명 미만이면 있는 만큼만 표시" 가 맞는지 기획 확인

**위 0.75ms 는 중복 제거가 없는 원본 조회다.** 최종 쿼리는 중복 제거가 붙으므로 다시 재야 한다
(200행 대상이라 미미할 것으로 보이나 확인 전이다).

### 4-6. 데이터 분포가 실행 계획을 바꾼다 — 기준선 재설정

여기까지의 수치는 전부 `seed` prefill 이 만든 분포 위에 있었다. 그 분포는 이렇다.

```sql
ON b.rn = ((seq.n - 1) % $USERS) + 1     -- 200명이 돌아가며 1건씩
```

**입찰자 200명이 물품마다 정확히 1건씩** 입찰한다. 그러면 `GROUP BY (물품, 입찰자)` 결과가
**물품당 200그룹**이 된다. 현실은 그렇지 않다 — 관심 있는 몇 명이 **여러 번** 주고받는다.

행 수는 4,000 으로 고정하고 물품당 입찰자만 20명(각 10건)으로 바꿔 다시 쟀다.

#### 실행 계획이 스스로 좋아졌다

| 분포 | 통계 | 계획 | 시간 |
|---|---|---|---|
| 200명/물품 | 오래됨 | `Table scan on u` (users 풀스캔) | 9.83 ms |
| 200명/물품 | 갱신 | `Table scan on u` **그대로** | 6.43 ms |
| **20명/물품** | 갱신 | **`Covering index range scan on b using idx_bids_item_bidder_amount`** + users PK 단일 룩업 | **2.92 ms** |

**`ANALYZE TABLE` 만으로는 계획이 바뀌지 않았다.** 분포가 원인이었다. 즉 [4-5](#4-5-실행-계획-explain-analyze)
에서 "리더보드용 인덱스를 쓰지 않는다"고 적은 것은 **그 분포에서만 그렇다.** 현실 분포에서는
옵티마이저가 알아서 최적 인덱스를 고른다.

#### 부하 수치도 5.4배 달라졌다

| | 입찰자 200명 (#4) | **입찰자 20명 (#7)** | |
|---|---|---|---|
| **입장 처리량** | 112.0 건/s | **609.0 건/s** | **5.4배** |
| p95 | 111 ms | **76 ms** | |
| 커넥션 획득 p95 | 79 ms | **5 ms** | 16배 개선 |
| `hikari_active_max` | 10 / 10 | 10 / 10 | 여전히 포화 |
| 누적 입장 | 20,272 | 110,235 | |

**`--bids-per-item` 은 200 으로 같다. 물품당 입찰자 수만 바꿨다.**

#### 현실 분포에서도 609건/s 에서 포화한다 (#7 → #8)

| | vus 10 | vus 20 | 배율 |
|---|---|---|---|
| **입장 처리량** | 609.0 건/s | 596.0 건/s | **0.98배** |
| p95 | 76 ms | 85 ms | 1.1배 |
| **커넥션 획득 p95** | **5 ms** | **80 ms** | **16배** |
| `hikari_pending_max` | 13 | 38 | 2.9배 |
| `hikari_active_max` | 10 / 10 | 10 / 10 | 포화 |
| 톰캣 스레드 | 24 / 200 | 49 / 200 | 여유 |
| `k6_cpu_max` | 36% | 35% | 무관 |

부하를 2배 올렸는데 처리량은 **오히려 줄었다(0.98배).** 판정 기준 1.2배에 한참 못 미친다.
톰캣과 부하 발생기는 한가한데 **커넥션 획득이 5ms → 80ms 로 16배** 뛰었다.

풀을 키우는 것은 답이 아니다 — #3 에서 이미 −14% 로 확인했다. MySQL(`cpus 2.0`)이 진짜 제약이고,
입장 하나가 SELECT 8회를 쓰는 구조가 원인이다.

#### 이 분포의 한계

prefill 은 `bidder = ((n-1) % 20) + 1` 라운드로빈이라 **각 입찰자의 입찰이 금액 전 구간에 고르게
흩어진다.** 실제 경매는 소수가 상위를 독점한다.

- **비용 측정에는 문제없다.** 비용을 좌우하는 행 수(4,000)와 그룹 수(20/물품)가 의도대로 나온다.
- **(C) LATERAL 의 정확성 위험은 이 데이터로 검증되지 않는다.** 금액 상위 20건이 정확히 20명
  것이라 `LIMIT 20` 이면 항상 3명이 확보된다. "두 명이 주고받으면 3위가 안 나온다"는 위험이
  드러나지 않는다. **그건 부하 테스트가 아니라 단위 테스트로 잡아야 한다.**

### 무엇이 병목인가

**현실적인 버스트에 6배 여유가 있다.** 짧은 버스트는 실패하지 않고 줄을 선다 — 5xx 는 모든

**현재 규모에서는 급히 고칠 것이 없다.** 609건/s 는 현실적인 버스트의 6배다. 아래는 필요해질

### Redis 를 넣지 않는 이유

처음에는 리더보드를 Redis ZSET 으로 빼는 안을 검토했다. **재보니 필요 없다.**

- **현재 규모에서 이미 6배 여유**가 있다 (609건/s vs 현실 버스트 100건/s)
- 더 필요하면 **쿼리 재작성만으로 4배**가 나온다. 새 의존성도, 파생 캐시 정합성도, 복구 경로도
  필요 없다
- 리더보드는 **입장할 때 1회성** 조회다. 그 뒤엔 SSE 가 갱신을 밀어주므로 폴링이 없어서, 조회
  빈도가 입장 속도(609건/s)에 묶여 있다. 그 정도 읽기를 위해 Redis 를 들일 이유가 없다
- `CLAUDE.md` 의 "DB 를 Source of Truth 로" 규칙상 Redis 는 항상 파생일 뿐이라, 정합성 관리
  비용만 늘고 원인은 그대로 남는다

쿼리 재작성 후에도 부족하면 그때 다시 검토한다. 서버 2대 확장 시 세션 외부화·SSE Pub/Sub 로
Redis 가 들어오면(`perf/README.md`) 한계비용이 낮아지므로 판단이 달라질 수 있다.

### 6-1. `findTopBidders` 쿼리 재작성

[4-5](#4-5-실행-계획-explain-analyze) 의 **(C) LATERAL 방식**을 기반으로 한다. 물품마다 상위 N건만
읽으므로 4,000행 → 200행이 되고, 현실 분포에서 단독 실행 기준 **4배**다 (2.92 → 0.73ms).

> 4-5 에 적힌 "약 10배" 는 최악 분포(9.83ms)와 비교한 값이다. 현실 분포 기준은 4배다.

구현 시 정해야 할 것:

1. **`LIMIT` 값** — 상위 N건에서 중복 제거해 3명을 만든다. 한 입찰자가 상위를 독점하면 3명이
   안 나오므로 20~30 정도로 넉넉히 잡는다 (그래도 4,000행보다 훨씬 싸다)
2. **3명 미만일 때의 처리** — fallback 쿼리를 둘지, "있는 만큼만 표시"가 맞는지 기획 확인
3. **중복 제거를 SQL 에서 할지 애플리케이션에서 할지**

**검증 순서:**

```
1) 단위·통합 테스트로 결과가 기존 쿼리와 같은지 (특히 같은 입찰자가 상위 여러 건을 가진 경우)
2) EXPLAIN ANALYZE 로 중복 제거를 포함한 최종 쿼리 시간 재측정
3) run.sh 로 before/after
```

```bash
./perf/run.sh --scenario 6 --items 20 --bids-per-item 200 --bidders-per-item 20 --vus 10 --prep-stmt on
```

before 는 **#7 현실 분포 기준선(609.0건/s, p95 76ms)** 이다. `--bidders-per-item 20` 을 빠뜨리면
최악 분포와 비교하게 되어 개선 폭이 5배 부풀려진다.

**`idx_bids_item_bidder_amount` 를 지우지 말 것.** 현실 분포에서 현재 쿼리가 이 인덱스를
`Covering index range scan` 으로 타고 있고, (C) 로 바꿔도 계속 쓰인다.

### 6-2. 입장 요청 3개 → 1개 (2순위, 공용 계약 변경)

합치면 ③④⑦이 사라져 **SELECT 8 → 4, 커넥션 획득 3회 → 1회**가 된다. API 계약 변경이라
프론트·백엔드·문서를 함께 갱신해야 하고 **팀 확인이 필요하다.**

1번을 먼저 하는 이유는 효과 차이가 20배이기 때문이다.

### 6-3. prepared statement 캐시 (3순위)

운영 JDBC URL 에 아래를 붙인다. 앱 코드 변경이 없다.

```
&cachePrepStmts=true&useServerPrepStmts=true&prepStmtCacheSize=250&prepStmtCacheSqlLimit=2048
```

운영 설정 변경이므로 팀 확인 후 적용한다.

### 6-4. 고친 뒤 다시 잴 것

- **입장 + 입찰 겹치기** — 이번 측정은 입찰이 0건이라 리더보드가 안 바뀐다. 실제 라이브 방은
  입찰이 섞이므로 캐시/비정규화의 효과가 이번 수치보다 낮을 수 있다
- **시나리오 1 (입찰 경합)** — 쿼리 재작성은 읽기 경로만 건드리므로 영향이 없어야 한다. 다만
  나중에 비정규화(물품 행에 상위 3명 유지)로 방향을 바꾸면 입찰 경로가 무거워지므로 그때는
  `lock_hold_p95_ms` 를 before/after 로 확인한다

## 미검증·한계

- **모든 실행이 `meta.json` 에 `dirty: true` 다.** 측정과 도구 수정을 함께 진행해서 커밋되지
  않은 변경 상태로 쟀다. 팀원이 그대로 재현할 수 없으므로 **`perf/` 변경을 커밋한 뒤 기준선
  한 줄을 다시 뜨는 것이 좋다.**
- **입찰이 도는 중에는 재지 않았다.** 시나리오 6 은 입장만 건다. 입장이 전부 동일한 응답을
  받았으므로 캐싱/비정규화 효과를 **과대평가**할 수 있다.
- **4-1~4-5 의 수치는 최악 분포 위에 있다.** 물품당 입찰자 200명(각 1건)이라는, 실제로는 나오지
  않는 분포다. 결론에 쓸 숫자는 [4-6](#4-6-데이터-분포가-실행-계획을-바꾼다--기준선-재설정) 이후의
  것이다. 이 절들을 지우지 않은 이유는 **"분포가 계획을 바꾼다"는 발견 자체가 결과**이기 때문이다.
- **현실 분포도 라운드로빈이라 편향이 없다.** 실제 경매는 소수가 상위를 독점한다. 비용 측정에는
  영향이 없지만(행 수·그룹 수가 목적대로 나온다), **(C) LATERAL 의 정확성 위험은 이 데이터로
  검증되지 않는다.**
- **"언제부터 아픈가"를 아직 재지 않았다.** [6-0](#6-0-먼저--언제부터-아픈가를-재서-우선순위를-확정한다)
  이 남아 있고, 그 결과로 6-1 의 우선순위가 정해진다.
- **VU 는 사람 수가 아니다.** 생각하는 시간이 없어 한 줄이 여러 명 몫을 한다. 잰 것은 "동시
  접속자 수"가 아니라 **입장 도착률**이다. 입장 후 SSE 로 머무는 인원은 시나리오 3 의 몫이다.
- **`ensureSession` 이 VU 당 한 번만 로그인하고 세션을 재사용한다.** 실제 입장자는 각자 세션이
  따로라, 이번 측정은 그만큼 실제보다 가볍다.
- **`select_per_bid` 8.0 중 7개만 코드에서 짚었다.** 나머지 1개는 미확인 — 실제 개선 작업 때
  쿼리 로그를 켜서 확인할 것.
- **EXPLAIN 은 진단용으로 손수 만든 데이터에서 떴다.** `run.sh` 가 만든 상태가 아니라, 실행이
  끝난 뒤 남아 있던 컨테이너에 물품 28개 · 입찰 5,600행을 SQL 로 밀어 넣고 그중 20개를 `IN` 절에
  넣었다. 행 수 형태는 측정 조건(20 x 200)과 같지만 **`run.sh` 로 재현되는 상태는 아니다.**
  개선 작업 때는 `perf/run.sh` 에 sweep_explain 처럼 리더보드 EXPLAIN 을 남기게 붙이는 편이 낫다.
- **(C) 의 0.75ms 는 중복 제거를 포함하지 않은 값이다.** 최종 쿼리는 다시 재야 한다.
- **단독 실행 시간과 부하 중 시간은 다르다.** 단독 7.9ms 가 측정에서는 입장당 106ms 였다
  (10 VU 가 MySQL `cpus 2.0` 을 나눠 쓴 경합). 재작성 효과도 부하 중에 다시 확인해야 한다.
- **`--prep-stmt on` 으로 잰 한 줄(`...11-45-00...`)의 `select_per_bid` 가 16.0 으로 찍혀 있다.**
  `com_select()` 를 `Com_select + Com_stmt_execute` 합산으로 바꿨던 때의 이중 계수이고 실제는
  8.0 이다. MySQL 은 prepared statement 실행 시 두 카운터를 모두 올린다(실측: `Com_select`
  186,711 / `Com_stmt_execute` 186,972). 지금은 `Com_select` 만 세도록 되돌렸다.
- **`results/` 의 2026-08-10 이전 측정은 워밍업이 없던 상태의 값**이라 이번 줄과 직접 비교하면
  안 된다.
- **MySQL `cpus: 2.0` 기준이다.** 운영은 RDS 라 스펙이 다를 수 있다. 다만 "입장 한 번이 4,000행을
  그룹핑한다"는 구조적 사실이라 스펙과 무관하게 개선 대상이다.
