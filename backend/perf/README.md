# 부하 측정 환경

주말 성능 측정용입니다 (이슈 #242). 다섯 명이 각자 노트북에서 **같은 조건으로** 재고
숫자를 합칠 수 있게 하려고 만들었습니다.

이 폴더는 **부하와 한계를 재는 곳**이고, 그 입구가 **개발 콘솔**입니다.
콘솔은 화면 확인과 부하 측정을 **한 페이지에서** 둘 다 합니다. 위쪽이 화면 확인,
아래쪽이 부하 테스트이고, **둘은 서로 다른 서버를 봅니다** (위는 개발 앱 `:8080`,
아래는 도커로 따로 띄우는 측정용 앱). 부하를 재도 개발 경매방은 그대로 남습니다.

**터미널을 쓰는 건 처음 설치할 때 한 번뿐입니다.** 그 뒤로는 파일 더블클릭과 브라우저
버튼으로 측정까지 끝납니다.

## 0. 설치 (딱 한 번)

넷을 깝니다. 이미 있으면 건너뜁니다.

| 무엇 | 어떻게 | 왜 |
|---|---|---|
| **Docker Desktop** | [docker.com](https://www.docker.com/products/docker-desktop) | MySQL, Grafana, 부하 발생기가 전부 도커로 뜹니다 |
| **Java 21** | `brew install --cask temurin@21` | 백엔드를 돌립니다 |
| **jq** | `brew install jq` | 스크립트가 결과에서 숫자를 뽑습니다 |
| **Python 3** | `xcode-select --install` (보통 이미 있습니다) | 브라우저 버튼으로 측정을 돌리는 작은 서버 |

k6는 안 깔아도 됩니다. `run.sh`가 도커 이미지로 띄우고, 그래서 다섯 명이 같은 버전을 씁니다.

**Docker Desktop 설정을 한 군데 바꿉니다.** Settings → Resources → CPUs 를 **6개 이상**으로
올립니다. 앱 2 + MySQL 2 를 주고 나면 나머지가 부하 발생기 몫이라, 4코어에서 돌리면 서버보다
부하 발생기가 먼저 막혀서 나온 숫자가 서버 한계가 아니게 됩니다.

프론트 화면까지 보려면 한 번 더 칩니다. 안 해도 부하 측정은 다 됩니다.

```bash
cd frontend && pnpm install
```

## 1. 켜기 (더블클릭 한 번)

Finder 에서 이 파일을 **더블클릭**합니다.

```
backend/UpBid 개발환경 켜기.command
```

터미널 창이 뜨지만 **아무것도 안 쳐도 됩니다.** 알아서 다섯을 순서대로 띄웁니다.

```
[1/5] 개발용 MySQL        준비됨
[2/5] 그래프              http://localhost:13000  (측정을 돌리기 전에는 비어 있습니다)
[3/5] 부하 테스트 콘솔 서버  http://localhost:18099
[4/5] 프론트              http://localhost:5173
[5/5] 백엔드 앱 — 뜨는 데 20초쯤 걸립니다

════════════════════════════════════════════════════════
  준비 완료. 아래를 브라우저에서 여세요.

     개발 콘솔   http://localhost:8080/dev-console.html
     그래프      http://localhost:13000
════════════════════════════════════════════════════════
```

**"준비 완료" 가 뜨면 그때부터 쓰면 됩니다.** 그 아래로 계속 흐르는 건 앱 로그입니다.

**이 창은 닫지 않습니다.** 닫으면 전부 멈춥니다.

<!-- 팀원이 실제로 이 둘을 고장으로 읽었다. 같은 질문이 또 나오지 않게 여기 적어 둔다. -->
헷갈리기 쉬운 것 둘을 미리 적어 둡니다.

- **Gradle 진행률이 `80% EXECUTING` 에서 안 움직이는 건 정상입니다.** 앱이 끝나지 않는
  작업이라 100% 가 될 일이 없습니다. 위에 `준비 완료` 가 찍혔으면 다 뜬 것입니다.
- **Grafana 는 측정을 돌리기 전까지 그래프가 비어 있습니다.** 접속은 되지만 그릴 숫자가
  아직 없기 때문입니다. 예전에는 측정을 한 번 돌려야 Grafana 자체가 떠서 그 전에는
  연결이 아예 안 됐는데, 지금은 이 런처가 미리 띄웁니다.

처음 한 번은 macOS 가 막을 수 있습니다. 그러면 Finder 에서 그 파일을 **우클릭 > 열기**로
실행합니다. **Docker Desktop 을 먼저 켜 둬야 합니다** — 안 켜져 있으면 창이 그렇게 알려주고
닫힙니다.

측정 콘솔만 따로 띄우려면 `perf/부하테스트-콘솔 켜기.command` 를 씁니다. 위 런처가 이미
띄우므로 보통은 쓸 일이 없습니다.

## 2. 개발 콘솔

앱을 `local` 프로파일로 띄우면 **<http://localhost:8080/dev-console.html>** 이 열립니다.
정적 파일이라 프론트를 안 띄워도 됩니다.

한 페이지에 구역이 둘입니다. 헤더의 링크로 그 자리로 뛰고, 헤더에는 **개발 경매방 상태와
측정 진행 상황이 늘 떠 있어서** 어느 쪽을 보고 있든 지금 뭐가 도는지 알 수 있습니다.

| 구역 | 무엇을 하나 | 어느 서버 |
|---|---|---|
| **화면 확인** | 방과 참여자를 만들고 자동 입찰을 켜서 **실제 경매방 화면이 움직이는 걸** 봅니다 | 개발 앱 `:8080`. 만든 방은 남습니다 |
| **부하 테스트** | 시나리오를 고르고 버튼을 눌러 **측정을 돌리고 결과를 쌓습니다** | 도커로 띄우는 측정용 앱. 실행마다 제 DB를 비웁니다 |

두 구역 모두 **번호 스텝을 순서대로 누르면 되고, 지금 눌러야 할 단계만 펼쳐집니다.**

### 화면 확인 구역

1. 경매방과 물품 만들기 (물품 수, 시작가, 입찰 단위)
2. 참여자 만들기 (약관 동의까지)
3. 물품 시작 (경매 시간. **1분으로 주면 Soft Close 연장과 마감까지** 보입니다)
4. 자동 입찰 반복 (입찰자 수, 간격)
5. **동시 입찰 검증** (아래 따로 설명)

지금 눌러야 할 단계만 펼쳐지고 나머지는 잠겨 있습니다. 프론트를 띄워 놓고 4번을 누르면
라이브 화면에 서로 다른 닉네임으로 입찰이 실시간으로 쌓입니다.

**콘솔에서 로그인한 사람이 프론트 화면에도 그대로 적용됩니다** (쿠키가 포트를 구분하지
않습니다). 그래서 자동 입찰을 켜고 나면 마지막 입찰자로 로그인된 상태가 됩니다. 판매자로
돌아오려면 1번의 [그 방에 이어서 쓰기]를 누릅니다.

<!-- 이 제약은 콘솔을 처음 보는 사람이 반드시 오해하는 지점이라 여기 적어 둔다 -->
**콘솔이 못 하는 것 둘.** 브라우저는 오리진당 세션 쿠키를 하나만 들고 `SESSION` 이
httpOnly 라 JS 가 직접 붙일 수 없어서, 4번의 "여러 명"은 계정을 갈아타며 **순차로** 흉내
낸 것입니다. 화면에는 여러 명이 입찰하는 걸로 똑같이 보이지만 **진짜 동시 입찰(락 경합)은
아닙니다.** SSE 동시 접속도 HTTP/1.1 에서 브라우저가 오리진당 6개로 막아 여기서는 못
만듭니다. 그 둘은 5번과 [부하 테스트] 구역이 맡습니다.

### 로그 보기

콘솔 **[부하 테스트] 구역 3번** 안에 로그 창이 있고, 탭 셋으로 나뉩니다. 무엇이 잘못됐는지는
대개 로그에 적혀 있는데, 터미널 창을 찾아 들어가야 하면 안 보게 됩니다.

| 탭 | 무엇 | 어디서 오나 |
|---|---|---|
| **측정 진행** | `run.sh` 가 찍는 것 그대로. 단계는 파랑, `※` 경고는 노랑, 실패는 빨강 | 콘솔 서버가 들고 있는 실행 출력 |
| **측정용 서버** | 측정용 앱이 뱉는 것 | `docker compose -f perf/docker-compose.perf.yml logs app` |
| **개발 서버** | 지금 띄워 둔 개발 앱이 뱉는 것 | `/tmp/upbid-backend.log` (런처가 남깁니다) |

**개발 서버 탭이 비어 있으면 런처를 한 번 다시 켭니다.** 앱 로그를 파일로도 남기게 된 건
이번 변경부터라, 그 전에 띄워 둔 앱은 터미널로만 흘리고 있습니다.

측정용 서버 탭은 **평소에 조용한 게 정상**입니다. `application-perf.yaml` 이 로그 수준을
`warn` 으로 내려 뒀기 때문입니다 (재는 대상이 서비스가 아니라 로그 출력이 되면 안 됩니다).
그래서 여기 뭔가 찍혔다면 대개 그게 원인입니다.

터미널에서 직접 보고 싶으면 이렇게 합니다.

```bash
docker compose -f perf/docker-compose.perf.yml logs -f app   # 측정용 앱
tail -f /tmp/upbid-backend.log                               # 개발 앱
tail -f /tmp/upbid-frontend.log                              # 프론트
tail -f /tmp/upbid-console-server.log                        # 콘솔 서버
```

### 그 밖의 개발용 페이지

| 주소 | 무엇 |
|---|---|
| <http://localhost:8080/sse-test.html> | 방에 SSE 로 붙어서 오가는 이벤트를 날것으로 봅니다. 화면이 안 바뀔 때 서버 문제인지 화면 문제인지 가릅니다 |

## 3. 측정 돌리기

콘솔 **[부하 테스트]** 구역에서 시나리오를 고르고 **[이 조건으로 실행]** 을 누릅니다.
진행 단계와 로그가 화면에 흐르고, 끝나면 결과표에 한 줄이 쌓입니다. 그래프 링크도 같이 뜹니다.

터미널이 편하면 같은 일을 이렇게도 합니다. 콘솔이 만들어 주는 명령과 같습니다.

```bash
ulimit -n 65535                                  # 측정할 셸에서 한 번
./perf/run.sh --scenario 1 --vus 40 --who 승민   # 계단 하나
open http://localhost:13000                      # 돌아가는 동안 그래프를 보고 있습니다
```

## 포트

**개발 환경은 8080과 5173 그대로 씁니다.** IntelliJ 실행 버튼이 기본으로 쓰는 값이라 옮기지
않았습니다. 대신 **측정 환경만 1xxxx 대역**으로 떨어뜨려서, 측정을 돌려도 개발 앱이 죽지
않게 했습니다.

| | 포트 | |
|---|---|---|
| perf nginx | **18080** | k6 가 때리는 유일한 입구. 사람이 열 일은 없습니다 |
| perf Prometheus | **19090** | 쿼리를 직접 해 보고 싶을 때 |
| perf Grafana | **13000** | **그래프.** 로그인 없이 들어갑니다. 3000 은 다른 개발 서버가 자주 씁니다 |
| 콘솔 서버 | **18099** | 위 `.command` 가 띄웁니다 |
| (개발 백엔드) | **8080** | **개발 콘솔이 여기 있습니다.** 측정이 건드리지 않습니다 |
| (프론트 vite) | 5173 | |

**`backend/.env` 는 손댈 것이 없습니다.** 개발 포트를 그대로 뒀기 때문입니다.

<!-- 이 브랜치가 한때 개발 포트를 18000/15173 으로 옮겼다가 되돌렸다. 그 사이에 브랜치를
     받아서 .env 를 고친 사람이 있어서 되돌리는 방법을 남겨 둔다. -->
다만 이 브랜치를 중간에 받아서 `.env` 를 18000 으로 고치셨다면 되돌려야 합니다. `.env` 값이
`application-local.yaml` 보다 우선해서, 옛 포트가 적혀 있으면 앱이 그쪽으로 뜹니다.

```
SERVER_PORT=8080
FRONTEND_URL=http://localhost:5173
KAKAO_REDIRECT_URI=http://localhost:8080/api/v1/oauth/kakao/callback
```

`frontend/.env` 의 `VITE_KAKAO_REDIRECT_URI` 도 같은 값으로 맞춥니다.

`PERF_HTTP_PORT` / `PERF_PROM_PORT` / `PERF_GRAFANA_PORT` 로 바꿀 수 있고, `run.sh` 는
**기동 전에 이 포트들이 비었는지 검사**해서 누가 잡고 있으면 그 프로세스 이름을 알려줍니다.

**한 대에서 측정을 두 개 동시에 못 돌립니다.** `run.sh` 가 잠금을 잡습니다. 두 번째 실행은
시작하자마자 거부됩니다 (앞 실행의 컨테이너를 내려 버려서 숫자가 조용히 망가지기 때문입니다).

## 측정 전에 챙길 것

- **`ulimit -n 65535`** — 측정할 셸에서 한 번. macOS 기본값이 낮아서 SSE를 수백 개 붙일 때
  먼저 터집니다. 서버 한계로 착각하기 딱 좋습니다.
- 측정 중에는 브라우저 탭과 다른 IDE를 정리합니다.
- 개발용 MySQL(`docker compose up`)은 켜 둬도 됩니다. 측정 환경은 프로젝트 이름이
  `upbid-perf`로 따로 놀고 포트도 안 겹칩니다.

측정용 앱과 MySQL은 호스트에 포트를 안 엽니다. `--scale app=2`로 늘릴 때 충돌하기
때문입니다. `cpus: 2.0`과 `mem_limit: 700m`은 배포 스펙과 같은 값이고, **토요일 오전에 가장
사양 낮은 노트북 기준으로 확정한 뒤에는 아무도 혼자 바꾸지 않습니다.**

코어 수만 `--cpus` 로 한 실행에서 바꿀 수 있습니다. 기본값을 바꾸라는 뜻이 아니라
**"CPU 가 천장인지" 를 한 쌍으로 확인하기 위한 것**입니다. 앱과 MySQL 이 함께 움직입니다.

## 시나리오

```bash
./perf/run.sh --scenario 0 --vus 160            # 부하 발생기 한계. 제일 먼저 돌립니다
./perf/run.sh --scenario 1 --vus 40 --items 1   # 한 물품 입찰 경합
./perf/run.sh --scenario 2 --vus 40 --items 20  # 여러 물품에 분산 (1의 비교군)
./perf/run.sh --scenario 3 --vus 400            # 실시간 접속 동시 연결 (회원이 필요 없어 --users 안 올려도 됩니다)
./perf/run.sh --scenario 4 --items 50           # 동시 마감
./perf/run.sh --scenario 1 --vus 40 --sse 800   # 5번. 입찰 + 실시간 접속 동시
./perf/run.sh --scenario 5 --vus 40 --items 20  # 6번. 마감 + 입찰 겹치기
```

계단은 **10 / 20 / 40 / 80 / 160**입니다. 한 번에 하나만 올리고 나머지는 그대로 둡니다.

**6번은 계단이 물품 수입니다** (5 / 10 / 20 / 50). 입찰자 수는 `--vus` 로 따로 줍니다.
4번과 달리 마감이 입찰의 물품 락을 기다리게 만드는 것이 목적이라 둘 다 필요합니다.

<!-- 실측으로 걸린 함정이라 적어 둔다. -->
6번은 **마감이 측정 구간 안에 안 들어올 수 있습니다.** 마감 임박 구간에 입찰이 들어오면
Soft Close 가 마감을 계속 미루기 때문입니다. 실제로 `--items 20 --vus 40` 으로 3분을 쟀더니
스케줄러 대기열은 69까지 쌓였는데 마감 지표는 전부 `NaN` 이었습니다. 마감 지연까지 보려면
`--duration` 을 늘립니다. 한 번에 하나만 올리고 나머지는 그대로 둡니다.

시나리오 1과 2는 입찰이라 **`--vus`가 `--users`(기본 200)보다 크면 `run.sh`가 막습니다.**
남는 VU는 약관 동의가 없어서 전부 `TERMS_NOT_AGREED`로 거절되기 때문입니다. 160을 넘겨서
재려면 `--users`도 같이 올립니다. 나머지 시나리오는 회원이 필요 없어서 그대로 둡니다.

확인 실험은 값을 **하나만** 바꿉니다.

```bash
./perf/run.sh --scenario 1 --vus 40 --pool 30        # 커넥션이 범인인지
./perf/run.sh --scenario 3 --vus 400 --heartbeat-ms 5000  # heartbeat가 마감을 밀어내는지
./perf/run.sh --scenario 4 --items 50 --scheduler-pool 8  # 스케줄러 스레드가 모자란지
./perf/run.sh --scenario 3 --vus 400 --xmx 512m           # 힙이 운영에서 터지는지
```

## 동시 입찰 검증 (부하가 아니라 정합성)

개발 콘솔 **[화면 확인] 구역 5번**입니다. 같은 물품에 N명이 **정확히 같은 순간에** 입찰하고,
결과가 규칙에 맞는지 넷을 확인합니다.

```
5xx·타임아웃이 없다
같은 금액이 두 번 접수되지 않았다        ← (auction_item_id, amount) unique
최종 현재가가 접수된 최고가와 같다
최종 1위가 그 입찰의 주인이다
```

부하 테스트와 목적이 다릅니다. **부하는 "몇 명까지 버티나", 이건 "동시에 들어와도 안 깨지나"**
입니다. 그래서 인원이 10명이어도 됩니다.

콘솔 서버가 사람마다 접속을 따로 만들고 스레드 배리어로 쏩니다. 브라우저로는 못 하는데,
오리진당 세션 쿠키가 하나뿐이라 한 번에 한 사람만 될 수 있기 때문입니다. 그래서 4번
"자동 입찰 반복"은 계정을 갈아타며 **순차로** 흉내 낸 것이라 락 경합이 아예 안 생깁니다.

**같은 금액으로 쐈을 때 거절이 `7006`(경합 충돌)이 아니라 `7004`(금액 부족)로 나오는 게
정상입니다.** 행 락이 줄을 세워서, 뒷사람이 자기 차례에 갱신된 현재가를 읽고 거절된 것입니다.
`7006` 이 나오면 그건 발견입니다.

### CPU 를 왜 세 컨테이너 따로 재는가

`k6_cpu_max` 하나만 있던 동안 **앱과 MySQL 의 CPU 를 한 번도 표에 안 올렸습니다.** pool 곡선을
20회 넘게 재고 "병목은 커넥션 풀" 이라고 결론까지 냈는데, 나중에 Prometheus 를 뒤져 보니
`process_cpu_usage` 가 pool 4 에서 평균 60 %, 시간의 15 % 는 100 % 에 붙어 있었습니다.
표에 없는 값은 아무도 안 봅니다.

세 칸이 답하는 질문이 다릅니다.

| | 이 값이 높으면 |
|---|---|
| `k6_cpu_max` | 부하 발생기가 못 따라간 것입니다. 그 줄은 버립니다 |
| `app_cpu_*` | 앱이 CPU 에 묶인 것입니다. `--cpus` 를 올려 한 줄 더 재서 확인합니다 |
| `mysql_cpu_*` | 커밋이 느린 이유가 디스크가 아니라 CPU 일 수 있습니다 |

마지막 칸이 중요한 이유가 하나 더 있습니다. **Docker Desktop on macOS 에서 `fsync` 는 디스크
대기가 아니라 호스트 CPU 작업입니다.** `performance_schema` 의 파일 I/O 시간은 그 이벤트에
머문 시간이라 CPU 인지 대기인지 안 가릅니다. `mysql_cpu_*` 가 그걸 밖에서 갈라 줍니다.

**CPU 가 천장인지 보는 법.** `--cpus` 를 올려 한 줄 더 잽니다. `accepted_per_s` 가 오르면
CPU 가 묶고 있던 것이고, 안 오르면 아닙니다. 다른 건 아무것도 바꾸지 않습니다.

```
./perf/run.sh --scenario 1 --vus 40 --pool 4 --items 1               # cpus 2.0
./perf/run.sh --scenario 1 --vus 40 --pool 4 --items 1 --cpus 4.0
```

`cpus` 를 바꾼 줄은 **기본값으로 잰 줄과 나란히 두고 비교하지 않습니다.** 이 한 쌍 안에서만 봅니다.

### 락 대기와 락 유지를 같이 보는 이유

`lock_wait_p95_ms` 하나만 보면 왜 오래 기다렸는지를 못 가릅니다. 줄이 길어서인지, 앞사람이
오래 잡고 있어서인지가 안 나오기 때문입니다. 그래서 잡고 있던 시간(`lock_hold_p95_ms`)을
같이 잽니다. 행 락은 커밋할 때 풀리므로 커밋까지 포함해서 잽니다.

| 대기 | 유지 | 읽는 법 |
|---|---|---|
| 큼 | 작음 | 줄이 긴 것입니다. 물품을 흩거나 요청 스트림을 줄이면 풀립니다 |
| 큼 | 큼 | 한 사람이 오래 잡고 있는 것입니다. 줄을 짧게 해도 안 풀리고, 락 안에서 뭘 하는지를 봐야 합니다 |

락 안에서 뭘 하는지는 `select_per_bid` 가 힌트를 줍니다. 입찰 한 건이 SELECT 를 여러 번
던지고 그게 락 안에 들어가 있으면, 왕복이 늘어난 만큼 다음 사람이 그대로 기다립니다.

### 갭 락을 보는 법

`--isolation RC` 로 한 줄 더 재고 `gap_locks` 를 비교합니다. RC 로 바꿨을 때 이 값이 0 으로
떨어지면서 처리량이 오르면 경합의 일부가 갭 락 때문이었다는 뜻입니다. 그대로면 물품 행 락
자체가 원인이라 격리 수준을 낮춰도 소용이 없습니다.

`results/{run_id}/data_locks.txt` 에 5초마다 뜬 표본이 그대로 남습니다. MySQL 은 넥스트키
락을 `LOCK_MODE` 에 그냥 `X` 로 적고, 행 하나만 잠근 것을 `X,REC_NOT_GAP` 으로 적습니다.

**지금 입찰 경로에서는 RR 로 재도 `gap_locks` 가 0 입니다.** 시나리오 1 을 RR 과 RC 로 한 줄씩
재서 확인했고 양쪽 다 표본이 `X,REC_NOT_GAP` 뿐이었습니다. 입찰이 물품을 기본키로 하나만
집어 잠그기 때문에 RR 에서도 갭을 물지 않습니다. 그래서 이 서비스에서는 격리 수준을 낮춰도
입찰 경합이 줄지 않습니다. 범위 조회를 잠그는 코드가 생기면 그때 이 값이 0 을 벗어납니다.

### 마감 조회가 표를 훑는지 보는 법

물품이 스무 개뿐이면 표 전체를 훑어도 순식간이라 인덱스가 있으나 없으나 같은 숫자가
나옵니다. `--bulk-items 100000` 으로 닫힌 물품을 채워 표를 불린 다음, `--sweep-index off`
와 `on` 을 한 줄씩 재서 비교합니다. `results/{run_id}/sweep_explain.txt` 에 실행 계획이
남으니 `type` 이 `ALL` 에서 `range` 로 바뀌었는지, `Using filesort` 가 사라졌는지를 봅니다.

**`results/` 안은 커밋하지 않습니다.** 다섯 명이 각자 수십 번 돌리면 저장소가 금방 무거워집니다.
`run.sh`가 마지막에 `index.csv` 한 줄을 그대로 찍어 주니, **그 줄을 노션 측정 결과 표에 붙여
넣어서 합칩니다.** 원본 시계열과 스크린샷은 각자 로컬에 남아 있으니 근거가 필요할 때 꺼내면 됩니다.

**실패한 실행도 지우지 않습니다.** `meta.json`과 `index.csv`의 `status` 칸에 `aborted`로
남습니다. 지우면 나중에 "이 계단은 왜 비었지"가 됩니다.

**`aborted` 줄은 노션에 붙여넣지 않습니다.** `run.sh`는 성공한 실행에서만 붙여넣을 줄을 찍고,
실패했으면 대신 다시 돌리라고 알려줍니다. 이 구분이 필요한 이유는 실패한 줄이 겉보기에
멀쩡하기 때문입니다. k6 가 중간에 죽으면 `summary.json` 이 없어서 접수와 거절이 전부 0 인데
처리량 칸에는 그럴듯한 숫자가 들어갑니다. 실제로 3분짜리 측정이 2분 07초에 끊긴 실행에
처리량 3490.7 이 박히고 접수가 0 으로 찍힌 적이 있습니다.

## 판정

부하를 두 배 올렸는데 처리량이 **1.2배도 안 오르는 첫 줄**을 찾습니다.
단, 그 줄에서 k6 CPU가 100%에 가까우면 보류합니다.

| 보이는 것 | 범인 |
|---|---|
| `hikari_pending_max`가 0보다 큼 | 커넥션 부족이거나, 락을 기다리며 커넥션을 붙잡음 |
| `tomcat_busy_max`가 200 근처 | 톰캣 스레드 고갈 |
| 힙이 GC 후에도 안 내려감 | 메모리 |
| **넷 다 여유로운데 안 오름** | **락 대기.** 자원은 노는데 한 줄로 선 상태 |

`pending`을 제일 자주 빠뜨립니다. `active 10/10`만 봐서는 "일하는 중"인지 "줄 서 있는 중"인지
구분이 안 됩니다.

**거절은 에러가 아닙니다.** `ALREADY_TOP_BIDDER`, `BID_AMOUNT_TOO_LOW`, `INVALID_BID_UNIT`,
`ITEM_CLOSED`는 규칙대로 거절한 정상 동작입니다. 진짜 실패는 5xx와 타임아웃뿐입니다.
`CONCURRENT_BID_CONFLICT`는 따로 셉니다 (행 락이 있어서 안 나오는 게 정상이고, **나오면
그게 발견입니다**). `note.md`에 종류별로 나뉘어 나옵니다.

## 무엇을 합칠 수 있고 무엇을 합칠 수 없나

`cpus: 2.0`은 **상한이지 하한이 아닙니다.** 같은 상한을 줘도 노트북마다 2코어의 성능 자체가
다릅니다. 그래서 **다섯 명의 절대 처리량은 못 합칩니다.**

합칠 수 있는 것은 각자의 **계단 비율**(두 배 올렸을 때 몇 배)과 그때 자원 넷이 어땠는지입니다.
판정 규칙이 마침 비율 기준이라 이건 그대로 성립합니다. 토요일 오전에 전원이 같은 조건으로
기본 부하를 한 번 돌려서 **숫자가 서로 얼마나 다른지 먼저 봅니다.** 크게 다르면 그 자체가 신호입니다.

## 자주 걸리는 함정

| 증상 | 진짜 원인 |
|---|---|
| SSE가 몇백 개에서 끊긴다 | `ulimit -n`. k6 셸에서 먼저 올립니다 |
| 앱이 CPU를 못 쓴다 | Docker Desktop 전체 리소스 상한 |
| 재현이 안 된다 | `run.sh`를 안 쓰고 손으로 돌렸습니다 (컨테이너 안 내림 / 워밍업 건너뜀) |
| 입찰이 전부 거절된다 | `note.md`의 "그 밖의 거절"이 0보다 크면 세션이나 약관 동의가 안 붙은 것입니다 |
| 처리량이 음수로 나온다 | 구간 앞뒤가 다른 컨테이너를 본 것입니다. `run.sh`가 `aborted`로 표시하니 다시 돌립니다 |
| 그래프에 실행이 여러 개 겹쳐 보인다 | Grafana 왼쪽 위 `실행` 선택기에서 이번 실행을 고릅니다 |

## 서버를 2대로 늘릴 때 (3주차 목요일)

```bash
docker compose -f perf/docker-compose.perf.yml up -d --scale app=2
docker compose -f perf/docker-compose.perf.yml restart nginx
```

nginx는 upstream 이름을 기동할 때 풀어서 들고 있어서 한 번 재시작해야 두 대를 봅니다.
Prometheus는 DNS로 찾으므로 그냥 둡니다.

**다만 지금 그대로 늘리면 깨집니다.** 넷을 먼저 고쳐야 하고 의존 순서가 있습니다.

| 순서 | 무엇 | 안 하면 |
|---|---|---|
| 1 | ~~`ddl-auto`를 `create`에서 바꾸기 (Flyway, #96)~~ **해결됨** | 스키마는 Flyway가 만들고 `ddl-auto`는 `validate`입니다. 마이그레이션 중에는 Flyway가 락을 잡아서 한쪽이 끝날 때까지 다른 쪽이 기다립니다 |
| 2 | 세션 외부화 (지금은 톰캣 메모리) | 요청이 다른 인스턴스로 갈 때마다 401이라 **부하 스크립트도 안 돕니다** |
| 3 | 중복 마감 방지 | 두 인스턴스가 같은 물품을 두 번 마감합니다. 성능이 아니라 **정합성** 문제입니다 |
| 4 | SSE를 프로세스 밖으로 (Pub/Sub 또는 `ip_hash`) | A 서버에서 입찰해도 B 서버에 붙은 사람은 못 받습니다 |

`AuctionCloseScheduler`가 인터페이스로 분리돼 있어서 3번은 구현을 갈아 끼울 자리가 있습니다.
`InMemoryVerificationCodeStore`도 같은 이유로 주석에 교체 계획이 적혀 있습니다.
