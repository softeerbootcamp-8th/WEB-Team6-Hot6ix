- 측정일 2026-08-11 21:09 ~ 21:30
- 코드 상태 `RoomSseManager.sendBroadCast()` 가 **요청 스레드에서 동기 전송**
  (커밋 `5e7c0a6` + uncommitted. `meta.json` 의 `dirty: true` 로 남아 있다)
- 비동기 전환 후 같은 4줄을 다시 재서 이 문서와 비교한다

## 재는 것

입찰 커밋 뒤 `@TransactionalEventListener(AFTER_COMMIT)` 가 방 전원에게 순차로
`emitter.send()` 를 돌린다. 이 전송이 요청 스레드 위에서 일어나므로 **접속 수가 늘면
입찰 응답 시간에 그대로 얹힌다**는 가설을 확인한다.

입찰자(VU)는 40으로 고정하고 SSE 접속 수만 0 → 100 → 200 → 400 으로 올린다.
나머지 조건(풀 10, 물품 1개, 격리 RR, heartbeat 30초)은 전부 동일하다.

### 파생값

| SSE | 전송 1건당 (p50 기준) | 접수 응답 중 broadcast 비중 | 브로드캐스트가 쓴 스레드시간 | 앱 2코어 중 |
|---|---|---|---|---|
| 100 | 19.4 µs | 14% | 0.34 초/초 | 17% |
| 200 | 19.9 µs | 23% | 0.74 초/초 | 37% |
| 400 | 22.3 µs | **38%** | **1.41 초/초** | **70%** |

- 전송 1건당 = broadcast p50 ÷ 접속 수
- 비중 = broadcast p50 ÷ 접수 p50 (두 중앙값의 비. 분해가 아니다)
- 스레드시간 = 브로드캐스트 건수 × broadcast 평균 ÷ 측정 구간
- 힙 증가분은 접속당 약 190 KB (109 → 128 → 143 → 189 MB)

## 판정

### 1. 브로드캐스트는 접속 수에 선형이다 — 확인

broadcast p50 이 1.94 → 3.98 → 8.93 ms 로 접속 수에 비례한다. 전송 1건당 비용이
19.4 / 19.9 / 22.3 µs 로 거의 상수다.

`hikari pending` 이 네 구간 모두 30(= VU 40 − 풀 10)으로 고정이다. DB 쪽 조건이 안 변했으므로
증가분을 다른 원인으로 돌릴 수 없다.

### 2. 접속 400명에서 입찰 응답의 38%가 브로드캐스트다 — 확인

접수된 입찰의 응답 중앙값 23.62 ms 중 브로드캐스트 중앙값이 8.93 ms 다.
동기 전송이 입찰 응답에 얹힌다는 가설의 직접 증거다.

### 3. 브로드캐스트를 안 하는 요청까지 느려진다 — 새로 발견

거절된 입찰은 커밋이 없어 브로드캐스트를 하지 않는다. 그런데 거절 p50 이
12.08 → 20.07 ms(+66%)로 접수와 같은 폭으로 느려졌다.

접속 400명에서 브로드캐스트가 앱 용량의 **70%**(1.41 초/초 ÷ 2코어)를 쓰기 때문이다.
**피해가 입찰에 국한되지 않는다.**

### 4. 400명이 무너지기 시작하는 지점이다

broadcast p50 은 200 → 400 에서 2.2배 오르는데 **p95 는 7.65 → 34.41 ms 로 4.5배** 뛴다.
평균(11.63)이 중앙값(8.93)보다 크다 — 꼬리가 길어졌다. 초당 121건 × 평균 11.6 ms 이면
항상 1.4개가 동시에 돌고 있어서 브로드캐스트끼리 다투기 시작한다.

heartbeat p95 도 1 → 15 ms 로 같이 나빠졌다. 이건 스케줄러 풀에서 돌고 물품 마감 예약과
풀을 공유하므로 **비동기 전환으로 고쳐지지 않는다. 별도 과제다.**

## 함정 (이 표를 읽을 때 반드시)

### `p95_ms`(혼합) 열로는 아무것도 못 본다

접수 비율이 0.8 ~ 8% 뿐이라, 섞은 분포의 p95 는 사실상 **거절된 입찰의 p95** 다.
거절은 브로드캐스트를 안 하므로 이 열은 접속 수에 거의 반응하지 않는다(45 → 42 → 46 → 61).
**반드시 상태 코드별로 갈라서 본다.**

### `처리량` 열로 "용량이 반토막"이라고 말하면 안 된다

2,968 → 1,451 req/s(−51%)지만, 접수는 24.7 → 121.7건/s 로 **5배 늘었다**. 거절이 싼 경로라
총 req/s 가 접수 비율에 끌려다닌다.

안전한 진술은 **접수율이 비슷한 100 → 400 구간의 −40%**(접수 134.5 → 121.7건/s, ±12%)다.
`sse 0` 은 접수율 0.83%로 혼자 튀어서 기준선으로 약하다.

### `접수 p50 − 거절 p50` 으로 브로드캐스트 몫을 추정하면 안 된다

그 차이가 3.55 ms 인데 broadcast p50 은 8.93 ms 다. 락을 오래 기다린 입찰은 그동안 현재가가
올라가서 거절될 확률이 높다(선택 편향). 그래서 거절 쪽 지연이 부풀려져 있고 두 집단의 구성이
다르다. 차이는 유효한 추정량이 아니다.

### 접수율이 실행마다 흔들린다

`bid.js` 의 금액이 `START_PRICE + BID_UNIT * (__ITER * VUS + __VU)` 로 그 VU 의 반복 횟수에
묶여 있다. 거절이 접수보다 싸므로 거절된 VU 가 더 빨리 반복하며 금액을 올리고, 앞서간 VU 하나가
현재가를 독점한다. 그래서 접수율이 통제되지 않고 실행마다 0.8 ~ 8% 로 흔들린다.

이 측정에서는 100/200/400 구간의 접수율이 우연히 ±12% 안에 들어와서 비교가 성립했다.
**다음에 같은 계단을 밟을 때 이 값이 다시 흔들릴 수 있으므로, 접수/s 를 먼저 확인하고
2배 이상 벌어진 구간은 다시 돌린다.**

## 재현 방법 (Prometheus 값)

`index.csv` 에 없는 열(상태 코드별 응답 분위, broadcast 분위)은 아래로 뽑는다.
컨테이너를 내리면 사라지므로 이 문서의 표가 원본이다.

```bash
RUN=2026-08-11T21-26-46_s1_vus40_pool10_items1_sse400
U='/api/v1/auction-items/{auctionItemId}/bids'
S=$(TZ=UTC date -j -f "%Y-%m-%dT%H:%M:%SZ" "$(jq -r .window.start perf/results/$RUN/meta.json)" +%s)
E=$(TZ=UTC date -j -f "%Y-%m-%dT%H:%M:%SZ" "$(jq -r .window.end   perf/results/$RUN/meta.json)" +%s)

# 접수(201)만의 p50. status="409" 로 바꾸면 거절, 0.95/0.99 로 바꾸면 다른 분위
B="http_server_requests_seconds_bucket{run=\"$RUN\", uri=\"$U\", status=\"201\"}"
curl -s -G http://localhost:19090/api/v1/query --data-urlencode "time=$E" \
  --data-urlencode "query=histogram_quantile(0.5, sum by (le) (($B @ $E) - (($B @ $S) or ($B @ $E) * 0)))*1000" \
  | jq -r '.data.result[0].value[1]'
```

`upbid_sse_broadcast_seconds_bucket{run="$RUN"}` 로 바꾸면 브로드캐스트 분위가 나온다.
시작 시점에 없던 계열을 0으로 채우는 `or ... * 0` 은 `run.sh` 의 `delta()` 와 같은 방식이다.

## 다음에 할 것

1. `RoomSseManager.sendBroadCast()` 를 `SseBroadcastExecutor` 로 넘기는 비동기 버전으로 되돌린다
   (`SseBroadcastConfig`: 풀 2, 큐 1000, `CallerRunsPolicy`)
2. 같은 4개를 돌린다. **판정 기준은 "접수 p50 이 계단에서 평평한가"** 다 — before 대비 절대값이
   아니라 계단 안의 추세라서, after 에서 접수율이 또 드리프트해도 판정이 흔들리지 않는다
3. 기대: 접수 p50 평평 / 처리량은 거의 그대로(일이 줄지 않으므로) / heartbeat p95 는 안 변함
4. `broadcast p50·p95` 는 before/after 로 비교하지 않는다. 동기에서는 응답 안의 시간이고
   비동기에서는 응답 밖의 시간이라 의미가 다르다

### 비동기 전환 전에 붙여야 하는 계측

비동기가 되면 `upbid.sse.broadcast` 는 **전송 루프만** 재고 큐에서 기다린 시간은 안 잡힌다.
그런데 브로드캐스트 스레드시간이 1.41 초/초이고 풀이 2스레드니 **스레드당 70% 사용률**이다.
이 수준에서는 큐 대기가 실제로 생기고, 그게 곧 이벤트가 화면에 늦게 도착하는 시간이다.

안 재면 after 결과가 "입찰은 빨라졌다, 이벤트 도착이 늦어졌는지는 모른다"가 된다.
비동기화의 유일한 리스크가 그것이므로 **큐 대기 타이머와 `CallerRunsPolicy` 발동 카운터**를
같이 넣는다.

## 미검증·한계

- **그 1.41 초/초가 CPU 인지 대기인지 안 갈렸다.** 전부 CPU 였다면 남은 30% 용량으로
  1,451 req/s 가 안 나온다(sse 0 이 100% 용량으로 2,968 req/s 였으니 계산상 890 정도).
  실제로 더 나왔으니 일부는 대기다. 다만 요청 쪽도 순수 CPU 가 아니라(DB 왕복) 증명은 아니다.
  `ThreadMXBean` 으로 브로드캐스트 구간의 CPU 시간을 wall time 과 나란히 재면 갈린다.
- **app CPU 가 네 구간 모두 100%** 다. 접속 0에서도 100%이므로 이 포화는 브로드캐스트가
  만든 것이 아니라 시나리오 1(vus 40, 물품 1개, 초당 2,700건 거절)의 기본 상태다. 다만 CPU
  여유가 없는 지점이라 **비동기화의 효과가 과소평가될 수 있다.**
- **톰캣 스레드 풀 고갈은 재지 못했다.** `tomcat_busy_max` 가 네 구간 모두 41(기본 200 스레드에
  VU 40)이라 원리적으로 고갈이 안 난다. 재려면 `max-threads` 를 낮추거나 VU 를 크게 올려야 한다.
- **느린 클라이언트가 없다.** 배경 SSE 는 `responseType: 'none'` 으로 루프백에서 본문을 즉시
  읽고 버린다. 소켓 송신 버퍼가 찰 일이 없으므로, 실제 모바일 사용자에서 발생할
  `emitter.send()` 블로킹은 이 측정에 존재하지 않는다.
- **`emitter.send()` 가 emitter 마다 payload 를 다시 직렬화한다.** `ResponseBodyEmitter` 가
  emitter 별로 메시지 컨버터를 타므로 접속 400개면 같은 DTO 를 400번 직렬화한다. 전송 1건당
  20 µs 의 상당 부분일 가능성이 있다. 비동기화와 별개의 개선(일 자체를 줄이는 쪽)이고
  아직 측정하지 않았다.
