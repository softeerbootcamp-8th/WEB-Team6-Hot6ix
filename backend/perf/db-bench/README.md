# 쿼리 하나를 인덱스 전후로 재는 곳

이슈 #335 에서 만들었습니다. **HTTP 부하와 상관없이 도는 쿼리를 재는 자리**입니다.

옆 폴더(`perf/`)의 k6 스택과는 목적이 다릅니다. k6 는 요청을 보내서 서버 한계를 재는
도구인데, 마감 예약 재동기화 쿼리는 트래픽과 무관하게 10초마다 도는 백그라운드 작업이라
요청을 아무리 보내도 실행 횟수가 안 변합니다. 그래서 앱도 nginx 도 안 띄우고 MySQL 만
따로 세워서 쿼리를 직접 돌립니다.

## 쓰는 법

Docker Desktop 만 켜져 있으면 됩니다.

```bash
./bench.sh                            # 1만, 10만, 100만 행을 차례로
./bench.sh --rows 100000              # 한 크기만
./bench.sh --rows 10000 --reads 300   # 읽기 횟수를 늘려서
./bench.sh --rows 10000 --keep        # 끝나고 MySQL 을 안 내림 (직접 붙어 볼 때)
```

한 크기마다 아래 순서로 돕니다. 인덱스 생성 전후로 표의 내용이 바뀌지 않게 짜 놓아서
두 라운드가 같은 데이터를 봅니다.

```
빈 MySQL → 스키마(V1, V2) → 시딩 → 읽기 → 쓰기 → 인덱스 생성 → 읽기 → 쓰기
```

결과는 `results/` 아래에 로그(`.log`)와 표(`.tsv`)로 남습니다. 커밋되지 않습니다.

```
tag                    n   min   p50   p95   p99   max   rows_examined  rows_sent
noidx-10000-read      100  1.28  1.32  1.48  1.51  1.53  10060          30
idx-10000-read        100  0.05  0.07  0.13  0.24  0.34  60             30
```

## 숫자를 어떻게 받아 오나

**시간은 클라이언트가 아니라 MySQL 이 준 값입니다.** `docker exec` 와 접속 왕복이 쿼리
시간과 자릿수가 같아서, 셸에서 재면 그게 통째로 섞입니다. 그래서 문장마다
`/*bench:태그*/` 주석을 달아 두고 `performance_schema.events_statements_history_long`
에서 그 태그로 골라 냅니다. 실행 하나하나의 시간(`TIMER_WAIT`)과 읽은 행 수
(`ROWS_EXAMINED`)가 같이 나옵니다.

`events_statements_history_long` 은 MySQL 8 기본이 OFF 라 compose 에서 켜 둡니다.

## 결과를 흔드는 것 세 가지

- **버퍼 풀.** 두 번째 실행부터 빨라지므로 128M 로 못 박고, 라운드마다 워밍업 20회를
  먼저 돌린 뒤에 잽니다. 100만 행이면 표가 이 크기를 넘어서 디스크를 읽게 됩니다.
- **같은 행을 두 번 쓰기.** 같은 값으로 덮으면 InnoDB 가 아무 일도 안 해서 인덱스 갱신
  비용이 0 으로 나옵니다. 그래서 `SOLD ↔ FAILED` 로 뒤집고, 마감 구간을 둘로 갈라
  라운드마다 다른 쪽을 씁니다.
- **커밋 fsync.** 단건 UPDATE 는 시간의 대부분이 커밋이라 인덱스 갱신이 묻힙니다. 그래서
  한 문장으로 1만 행을 바꾸는 측정(`-bulk` 태그)을 같이 둡니다.

## 파일

| 파일 | 무엇 |
|---|---|
| `bench.sh` | 전체 흐름. 여기만 부르면 됩니다 |
| `docker-compose.db-bench.yml` | 전용 MySQL. 프로젝트 이름이 `upbid-dbbench` 라 개발용과 따로 놉니다 |
| `sql/seed_base.sql` | 판매자, 상품, 경매방 |
| `sql/seed_items.sql` | 물품. 상태 분포를 실제와 맞춥니다 (진행중 소수, 마감된 것이 대부분) |
| `sql/stats.sql` | 태그로 골라 p50, p95, p99 와 읽은 행 수를 뽑습니다 |
