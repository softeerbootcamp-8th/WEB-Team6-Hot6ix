# 시연용 테스트 데이터

시연 전에 보여줄 경매방과 물품을 미리 넣어두는 스크립트입니다. 이슈 [#333](https://github.com/softeerbootcamp-8th/WEB-Team6-Hot6ix/issues/333).

부하 측정용 시드는 여기가 아니라 `backend/perf/seed.sh`에 있습니다. 그쪽은 API를 호출하고
dev-login으로 가상 사용자를 만드는 반면, 여기는 운영 DB에 SQL로 직접 넣습니다.

| 파일 | 하는 일 |
|---|---|
| `seed-demo-data.sql` | 경매방 3개, 상품 24개, 물품 24개, 입찰 27건을 넣습니다 |
| `seed-events.py` | 방에 들어갔을 때 보이는 알림 피드를 미리 채웁니다 |
| `cleanup-demo-data.sql` | 그 방과 상품을 `deleted_at`으로 가립니다 |

넣는 데이터는 방마다 물품 8개이고, 그중 3개가 진행 중이고 5개가 대기입니다.
한 방에 진행 중인 물품은 3개까지라(`MAX_IN_PROGRESS_PER_ROOM`, 운영 기본값 3)
그 이상은 서비스가 스스로 만들 수 없는 상태가 됩니다.

## 넣기 전에 준비할 것

1. **판매자 계정을 만듭니다.** 카카오로 로그인하고 판매자 등록까지 화면에서 마칩니다.
   스크립트는 계정과 판매자 프로필을 만들지 않고 찾기만 합니다.
2. **`@seller_store_name`을 채웁니다.** 판매자 등록할 때 입력한 가게 이름 그대로입니다.
   DB를 뒤질 필요 없이 화면에서 아는 값으로 지정하려고 이걸 기준으로 찾습니다.
   같은 이름을 쓰는 판매자가 둘 이상이면 아무것도 넣지 않고 멈춥니다.

사진은 이미 채워져 있습니다. 아래 "사진은 Unsplash 링크입니다"를 보세요.

## 넣기

```bash
mysql -h {host} -u {user} -p --default-character-set=utf8mb4 {db} \
    < backend/demo/seed-demo-data.sql
```

`--default-character-set=utf8mb4`를 빼면 한글이 깨져서 들어갑니다.

끝나면 방마다 진행 중 3개와 대기 5개가 표로 찍힙니다. 그게 안 나오면 들어간 게 없는 겁니다.

문구와 사진 URL은 스크립트 안 `demo_seed_rooms`와 `demo_seed_items` 두 표만 고치면 됩니다.
그 아래는 손댈 일이 없습니다.

## 입찰 내역도 같이 들어갑니다

`@seed_bids = 1`이면 입찰자 6명을 만들고 진행 중 물품마다 3건씩 넣습니다. 리더보드가 상위
3명을 보여주므로 방에 들어오자마자 순위표가 차 있습니다. 0으로 두면 시작가 그대로 둡니다.

- **입찰자는 SQL로 만든 계정이라 로그인이 안 됩니다.** 리더보드에 이름이 보이는 용도입니다.
- **반드시 처음 넣을 때 같이 넣어야 합니다.** Redis에 그 물품 상태가 한 번 만들어지면
  나중에 MySQL을 고쳐도 Redis는 덮어쓰지 않습니다. 옛 스냅샷으로 되돌리지 않으려고 일부러
  그렇게 돼 있습니다(`AuctionRedisStore.seed`). 뒤늦게 넣고 싶으면 그 물품의
  `auction:item:{id}` 키를 지워서 다시 읽게 만들어야 합니다.
- **`current_price`와 `leader_user_id`를 마지막 입찰과 맞춰서 넣습니다.** Redis Seed가 이
  값을 읽어가므로 어긋나면 화면과 입찰 판정이 갈립니다.

## 사진은 Unsplash 링크입니다

상품 24장과 방 커버 3장 모두 `https://images.unsplash.com/...` 주소를 `image_url`에 그대로
넣습니다. 사진 파일이 우리 S3로 복사되는 게 아니라, 화면이 그 주소를 바로 불러옵니다.
상업적 사용이 허용된 라이선스입니다.

**그래서 이 상품들은 판매자 화면에서 수정할 수 없습니다.** `ImageUrlValidator`가 우리 버킷
주소로 시작하지 않는 `imageUrl`을 `INVALID_IMAGE_URL`로 거절하기 때문입니다. 저장 자체는
SQL로 넣어서 검증을 지나지 않았고, 조회와 입찰에는 영향이 없습니다. 수정까지 필요해지면
그 상품 사진만 판매자 화면으로 다시 올려서 S3 주소로 바꿔야 합니다.

## 알림 피드 채우기

SQL 로 심은 입찰은 알림 피드에 아무것도 남기지 않습니다. 피드에 뜨는 이벤트는 입찰 API 가
발행해 Redis 에 쌓는 것이라, DB 에 행을 넣는 것만으로는 생기지 않기 때문입니다. 방에
들어가자마자 최근 이벤트가 보이게 하려면 SQL 을 돌린 뒤 이걸 한 번 더 돌립니다.

```bash
export MYSQL_PWD='...'
MYSQL_CMD='mysql -h {host} -u {user} --default-character-set=utf8mb4 {db}' \
REDIS_CMD='redis-cli -h {host} --pipe' \
python3 backend/demo/seed-events.py
```

- **먼저 `--dry-run`으로 확인할 수 있습니다.** Redis 에 쓰지 않고 무엇이 들어갈지만 보여줍니다.
- **운영 Redis 가 TLS 면 `REDIS_CMD`에 `--tls`를, 비밀번호가 있으면 `-a`를 함께 넘깁니다.**
- **방마다 이벤트 12건이 들어갑니다.** 물품 시작 3건과 입찰 9건입니다. 프론트는 최근 20건까지
  받아 그립니다.
- **이미 실제 이벤트가 쌓인 방에는 돌리지 마세요.** 중복을 막으려고 그 방 버퍼를 먼저 비웁니다.
- **그 뒤에 들어오는 실제 입찰은 이어서 쌓입니다.** 순번 카운터를 마지막 번호로 맞춰 둡니다.

## 넣은 뒤

- **공유 링크는 `{프론트 주소}/join/{share_code}`입니다.** 세 방의 `share_code`는 스크립트
  맨 위에 박혀 있어서, QR도 미리 만들어 둘 수 있습니다.
- **마감 예약과 Redis 입찰 Seed는 따로 손댈 게 없습니다.** `AuctionRecoveryRunner`와
  `AuctionRedisSeedRecoveryRunner`가 진행 중인 물품을 주기적으로 다시 읽어 갑니다.
  서버를 재시작할 필요는 없습니다.
- **실제로 입찰까지 되는지 한 번 확인합니다.** 링크로 들어가서 약관 동의하고 입찰 버튼을
  눌러봅니다.

## 정리

```bash
mysql -h {host} -u {user} -p --default-character-set=utf8mb4 {db} \
    < backend/demo/cleanup-demo-data.sql
```

행을 지우지 않고 `deleted_at`만 채웁니다. 잘못 돌렸으면 그 값을 `NULL`로 되돌리면 됩니다.

**방 공개 조회 캐시는 따로 지워야 합니다.** 안 지우면 최대 5분간 지워진 방이 그대로 보입니다.
명령은 `cleanup-demo-data.sql` 아래쪽 주석에 적어뒀습니다.

## 알아둘 것

- **판매자가 방 종료를 누르면 그 방은 되돌릴 수 없습니다.** 되살리는 API가 없어서 스크립트를
  다시 돌려야 하는데, `share_code`가 이미 쓰인 값이라 새로 뽑아 두 스크립트에 고쳐 넣어야
  합니다. 그러면 미리 만들어 둔 링크와 QR도 같이 바뀝니다. 시연 중에는 방 종료를 누르지
  않는 편이 낫습니다.
- **아무도 입찰하지 않은 물품은 마감될 때 시드용 입찰자가 낙찰자가 됩니다.** 그 계정은
  로그인이 안 되니 거래가 더 진행되지 않습니다. 신경 쓰이면 `@seed_bids = 0`으로 넣습니다.
- **같은 스크립트를 두 번 돌리면 `share_code` 중복으로 멈춥니다.** 데이터가 두 벌 생기지
  않게 일부러 그렇게 뒀습니다. 정리한 뒤 다시 넣으려면 방 세 개의 `share_code`를 새로
  뽑아서 두 스크립트에 함께 고쳐 넣으세요. 영문 대소문자와 숫자 16자입니다.

  ```bash
  LC_ALL=C tr -dc 'A-Za-z0-9' < /dev/urandom | head -c 48 | fold -w 16
  ```

- **판매자를 못 찾으면 아무것도 넣지 않고 멈춥니다.** 그때 나오는 에러 메시지가
  `Table '...판매자를_못_찾음_가게_이름_확인' doesn't exist`입니다. 없는 테이블 이름으로
  일부러 멈추는 것이라, 저 이름이 보이면 `@seller_store_name`을 확인하면 됩니다.
- **진행 중인 물품은 12시간 뒤에 닫힙니다.** 경매 시간 상한이 720분이라
  (`AuctionItemStartRequestDto`) 그보다 길게 넣으면 화면에서는 만들 수 없는 물품이 됩니다.
  12시간이 지나도 **방은 계속 열려 있습니다.** 대기 물품이 하나라도 남아 있으면 방치된 방
  자동 종료 대상에서 빠지기 때문입니다(`AuctionRoomRepository.findIdleRoomIds`). 다시
  입찰을 받으려면 판매자 화면에서 대기 물품을 시작하면 됩니다.
- **정리 뒤에도 물품 행은 남습니다.** `auction_items`에는 `deleted_at`이 없습니다. 방이
  가려지면 화면에서는 안 보이지만, 진행 중이던 물품은 `end_at`이 될 때까지 마감 예약에
  붙들려 있다가 그때 닫힙니다. 바로 떼는 방법은 `cleanup-demo-data.sql` 맨 아래 주석에
  적어뒀습니다.
